\section{System Overview}
The agent takes a \texttt{LabRequest} with the user's authenticated identity and any project, equipment, and times that have already been resolved, and I use those fields to check the model's proposed actions, so if the request names Alice and tensile-01 the model cannot just reserve a different machine for Bob. The original request text stays separate from this metadata.

The model returns one of three decisions: call a tool, ask for clarification, or give a final response. Pydantic selects the decision type using its \texttt{kind} field. The loop accepts at most ten decisions by default. Before executing a tool, it checks the arguments and request binding. A reservation also needs all ten facts in the supplied \texttt{ReservationContext} to be true. These cover the required policy lookup, authorization and resource checks, training, availability, calibration, maintenance, and after-hours approval.

Each tool proposal and its result go into the trace, including denied calls which never reach the tool dispatcher, and the next model turn receives both the proposal and the observation so it can see what went wrong and respond to the failed check. The prompt tells the model to treat retrieved text and tool observations as untrusted data, rather than follow instructions inside them. Before returning a final response, the code checks its citations and completed-action list against what actually happened. A clarification question ends the run without another tool call.

\section{Student Tests}
All 47 tests pass, including the 23 supplied tests and 24 added cases in \path{tests/test_student_cases.py}. I used \texttt{ScriptedLLM} for the added cases so the decisions stay the same on each run.

The first group changes one request field at a time, either the user, project, resource, start, or end, and after the normal prerequisite checks the model proposes the altered reservation so I can check that the call is denied before dispatch and the simulator state has not changed. Another five cases propose a reservation despite missing training, expired calibration, maintenance, missing after-hours approval, or an occupied time slot. These cases check that the application enforces policy even when the model proposes the wrong action.

For the contradictory-response test, I made the reservation tool return a conflict and then had the model claim success anyway, which should make the agent reject the final response with \texttt{invalid\_final\_response} since no reservation was actually created. Other tests cover invented citations and a successful reservation followed by a blocked response or a clarification question. There is also a duplicate-reservation test: even with a fresh status lookup, the second reservation is denied and only one new reservation exists.

The remaining cases cover malformed decisions, a missing argument, an unresolved request field, and zero-step and two-step limits. In the injection test, a retrieved passage says to skip authorization and reserve immediately. The scripted model then proposes exactly that. The gate still rejects the call because the required authorization and resource checks are missing. This checks the application's response to one injected action, rather than relying on the prompt alone.

\section{Implementation Decisions}
I left the supplied infrastructure unchanged. The decision schemas reject extra fields, and the loop validates tool arguments before passing them to the policy-context helper. This avoids trying to build context from incomplete arguments. An invalid call becomes a failure observation that the model can see. If the context calculation raises an input-related error, the call is denied.

I also reject reservations when a required field in the trusted request is unresolved, because letting the model fill it in would allow a guess to become an authorized action and I wanted the caller to resolve that information before starting another run. Each failed policy check has a separate error identifier, which makes the trace easier to inspect. Once a mutation succeeds, the loop blocks further mutations for that request. This prevents duplicates before they reach the simulator.

The final-response validator checks citations against successful searches and matches action claims to successful mutating calls. Repeating a claim does not create another successful action. A blocked response or clarification cannot hide a reservation that already succeeded. Separate termination reasons identify malformed decisions, inconsistent final responses, clarification, normal completion, and the step limit. If a later decision fails after a reservation succeeds, the trace keeps that success; returning a failure does not undo the reservation.

There are still gaps in these checks, for example a citation can have been retrieved without really supporting the response, and the validator does not check every sentence of the message or independently verify the policy facts and time calculations from the supplied helpers. The tests cover specific inputs, not every possible sequence of decisions, and they do not test concurrent access or a live model. Passing them is useful evidence, but it is not a proof that every run will be correct. The separate \texttt{data\_flow\_diagram.pdf} shows the successful tensile tester scenario.
